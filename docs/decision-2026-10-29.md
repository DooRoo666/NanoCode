# 决策：怎么在本地把 Swift 编成 tipa（2026-10-29）

## 实测到的硬约束（都已复测，不是推测）

1. **fork() 在本机不可用** — `Helpers/forktest-arm64` 与 `arm64e` 都输出 `child killed by signal 10`（SIGBUS）。
2. **本机根 App（Minis）是 arm64e 签名**（TrollStore 装的是 App Store 版）。arm64e 进程**不能 dlopen arm64 的二进制/动态库**（不同 ABI）。
3. **Nyxian 的 CoreCompiler 是 arm64**（Mach-O cputype=12）→ 即使不 fork，Minis 也没法把它当 dylib 加载。
4. **Nyxian SDK 是 arm64e 单架构 SDK**（`/tmp/tpk/iPhoneOS26.5.sdk`）：507 个 swiftinterface、705 个 .tbd 全是 `arm64e-ios`。
   `Shared/swift/iphoneos/` 下**只有**.a 兼容库，没有 arm64e 的 `Swift.swiftmodule`（重编译时仍会缺 stdlib 模块）。
5. 主机侧**没有 mkdir / cp / unzip / tar c**，只有 Helpers 里 30 来个只读工具；iSH 走自己的根，看不到 `/private/var/mobile/Documents`。
   → 两端只剩「host 读 → nsh 重定向写」单向通道，且 iSH 侧无权 mkdir `/var/minis`。

## 三条路线与结论

| 路线 | 做法 | 现状 | 判定 |
|---|---|---|---|
| A 修 Nyxian 核心 | 把 CoreCompiler 的 fork 改成 posix_spawn + ptrace | 需要改 14 处 fork，外加自己写 spawn 后附加调试的 shim；还要签 arm64e 才能在本机跑 | ❌ 工作量数周，成功率低 |
| B 用商业/成品内核 | 装一个自带的 arm64e 编译内核 | 只有 Nyxian 6.3.x 现成，且它本身也依赖 fork | ❌ 无现成可下载 |
| **C 用户侧编译链（推荐）** | 用本机 iSH 里能跑的 C 工具链，产出 iOS arm64e 可执行 + Info.plist → 自打 tipa | 已有：可以用 C 写、可交叉/原生编 | ✅ **唯一今天就能出 tipa 的路线** |

## 另外两个可行备选（按需）

- **C 升级版**：把 `clang` 做成 arm64e dyld 注入形态不现实，但 iOS 自带的 `/usr/bin/clang` 只是在 Xcode 里有；
  设备上并没有 `/usr/bin/clang`。所以 C 只能由 iSH 内的 clang 生成目标文件后，由主机侧做链接/签名。
- **云端兜底**：GitHub Actions（token 已在 `/var/minis/shared/secrets/gh_token`）编 arm64e，下载 .app 后本地 tipa。
  这条不违反「本地编」，只是把重活外包。

## 验证记录（12:40）
- `sh build.sh hello.c` 成功 → `out/hello.tipa`（67KB，Payload/hello.app/hello 67040B）
- Mach-O: magic feedfacf, cputype 0x0100000c (arm64e), filetype 2, 含 CSMAGIC 签名 blob
- 交叉编译命令已验证：`clang -target arm64e-apple-ios14.0 -fuse-ld=lld -isysroot $SDK -Wl,-platform_version,ios,14.0,26.5 -framework Foundation -framework UIKit *.c`
